# icslint

A command-line checker for `.ics` (iCalendar, RFC 5545) files.

Most tools that read calendar files either accept broken input silently or
fail with something like `ValueError: invalid calendar` and no indication
of where in the file the problem is. Calendar exports get hand-edited,
copy-pasted between systems, or generated by scripts with off-by-one bugs
in their line folding, and when that happens you're left bisecting a
thousand-line file by hand. icslint parses the file itself, tracks the
exact line and column of every token as it goes, and reports problems the
way a compiler would: file, line, column, the offending source line, and a
caret under the exact spot.

## Usage

```
python -m icslint path/to/calendar.ics
```

or, after installing (`pip install -e .`), just:

```
icslint path/to/calendar.ics
```

Pass `-`, or nothing at all, to read from stdin instead of a file:

```
cat path/to/calendar.ics | icslint
```

Pass `--strict` to also run pedantic checks that flag things RFC 5545
discourages without making the file unreadable: content lines longer than
75 octets (3.1) that a well-behaved writer would have folded, and a
`VERSION` value other than `2.0` (3.7.4, the only value the RFC defines).
These are off by default because plenty of calendars in the wild violate
them harmlessly.

Exit code is `0` if the file is well-formed, `1` if it has errors, `2` if
the path couldn't be read.

## Example

Given a file `broken.ics`:

```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//example//icslint//EN
BEGIN:VEVENT
UID:1234@example.com
DTSTAMP:20260101T090000Z
DTSTART20260102T090000Z
SUMMARY:Missing colon above
END:VEVENT
END:VCALENDAR
```

`icslint broken.ics` prints:

```
broken.ics:7:24: error: content line is missing the ':' that separates the name/parameters from the value
  DTSTART20260102T090000Z
                       ^
```

The name-parsing rule doesn't know `DTSTART20260102T090000Z` was meant to
be `DTSTART:20260102T090000Z` -- it just knows a valid content line always
has a colon somewhere, and points at the exact spot where it expected one.

## What it checks right now

- Line unfolding (RFC 5545 3.1): continuation lines starting with a space
  or tab are joined to the previous line, with position tracking preserved
  through the join.
- Content line syntax: `NAME *(;PARAM=VALUE) : VALUE`, including quoted
  and comma-separated parameter values.
- `BEGIN`/`END` nesting: unmatched, mismatched, or unclosed blocks are
  reported at the line that opened them, not just where things went wrong.
- Exactly one top-level `BEGIN:VCALENDAR` block.
- Required properties: `VERSION` and `PRODID` on `VCALENDAR`, `UID`,
  `DTSTAMP`, and `DTSTART` on every `VEVENT`.
- Duplicate `UID`s across `VEVENT`s in the same file, reported at the
  duplicate with a pointer back to the `VEVENT` that used it first.
- `DATE`/`DATE-TIME` value formats: `DTSTART`, `DTEND`, `DUE`,
  `RECURRENCE-ID`, and `EXDATE` are checked against their `VALUE` parameter
  (`DATE` or `DATE-TIME`, defaulting to `DATE-TIME`), including that the
  calendar date itself is real (no Feb 30, no leap days in non-leap years).
  `DTSTAMP`, `CREATED`, and `LAST-MODIFIED` are checked as UTC `DATE-TIME`
  values, since RFC 5545 doesn't let those vary. `EXDATE` and `RDATE`
  values are checked item-by-item when comma-separated.
- `RRULE` syntax (RFC 5545 3.3.10): every part must be a recognized
  `NAME=VALUE` pair (or an `X-` extension), `FREQ` is required and must be
  one of the eight defined frequencies, `COUNT` and `INTERVAL` must be
  positive integers, `UNTIL` must be a valid `DATE` or UTC `DATE-TIME`, and
  `UNTIL`/`COUNT` may not both appear on the same rule.

Timezone reference checks are not implemented yet -- see the roadmap below.

With `--strict`:

- Content lines over 75 octets that should have been folded.
- `VERSION` values other than `2.0`.

## Why no dependencies

Standard library only, no build step beyond what `pip install -e .` already
does. A file linter should be something you can drop into a CI job or a
pre-commit hook without pulling in a dependency tree.

## Status

Early. The parser and BEGIN/END structural checks work; the rule set is
still small. Not yet published anywhere.
